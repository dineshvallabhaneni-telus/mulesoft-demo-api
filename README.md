GitHub Actions Workflows

The repository contains three workflow files:

.github/
└── workflows/
    ├── ci.yml
    ├── promote.yml
    └── reusable-deploy.yml

1. ci.yml

This is the main CI/CD workflow.

It runs automatically when code is pushed to the develop branch.

The workflow performs:

Checkout source code.
Setup Java 17.
Calculate the application version.
Build the Mule application with Maven.
Run the required tests.
Create the Mule application JAR.
Add version, branch name, and commit hash to the artifact name.
Upload the JAR as a GitHub Actions artifact.
Automatically deploy the artifact to DEV.

Example artifact:

mulesoft-demo-api-1.0.1-develop-b64f946.jar


The GitHub Actions artifact is stored as:

mule-application-1.0.1


The same artifact is used for subsequent promotions.

2. reusable-deploy.yml

This is a reusable GitHub Actions workflow.

It is responsible for deploying the already-built Mule application to CloudHub 2.0.

It does not build the application again.

It:

Receives the GitHub Actions run ID.
Finds the artifact generated by ci.yml.
Downloads the artifact.
Sets up Java/Maven.
Deploys the JAR to the requested CloudHub environment.

The workflow can be used for:

DEV
QA
UAT
PROD


The target environment is supplied by the calling workflow.

This ensures that the same application artifact can be promoted through the environments.

3. promote.yml

This workflow is used for manual promotion.

It is triggered from:

GitHub → Actions → Promote Mule Application → Run workflow


The user selects the target environment:

QA
UAT
PROD


The application version does not need to be entered manually.

The workflow identifies the successful CI build and downloads the artifact generated by that build.

Example:

CI Build
   │
   └── mulesoft-demo-api-1.0.1-develop-b64f946.jar
                         │
                         ▼
                        DEV
                         │
                         ▼
                        QA
                         │
                         ▼
                        UAT
                         │
                         ▼
                       PROD


The application is not rebuilt during promotion.

Important: Secrets vs Variables

The following values should be stored as Secrets:

ANYPOINT_CLIENT_ID
ANYPOINT_CLIENT_SECRET


The following can be stored as Variables if you prefer:

ANYPOINT_ENVIRONMENT
ANYPOINT_TARGET
APPLICATION_NAME


If the workflows are currently configured to use secrets.*, keep them as Environment Secrets.

Do not commit Client IDs or Client Secrets into the repository.

CloudHub Target

ANYPOINT_TARGET must exactly match the CloudHub 2.0 target available in the selected Anypoint Platform environment.

For example:

CloudHub-US-East-1


or:

CloudHub-US-East-2


The value is case-sensitive and must correspond to an actual CloudHub target.

If the target does not exist, deployment will fail with an error similar to:

Could not find target CloudHub-US-East-2

Application Names

Use a different CloudHub application name for each environment.

For example:

DEV
api-dev

QA
api-qa

UAT
api-uat

PROD
api-prod


This prevents deployments to one environment from overwriting the application in another environment.

Versioning

The application version is generated automatically by ci.yml.

The user does not enter the version manually.

For example:

First build
1.0.1

Next build
1.0.2

Next build
1.0.3


The version is passed to Maven using:

-Drevision=<version>


The POM uses:

<version>${revision}</version>

Artifact Naming

The generated JAR is renamed using:

application-version-branch-commit.jar


For example:

mulesoft-demo-api-1.0.1-develop-b64f946.jar


Where:

mulesoft-demo-api
        │
        ├── Application name
        │
        ├── 1.0.1
        │      Version
        │
        ├── develop
        │      Branch
        │
        └── b64f946
               Git commit hash


The GitHub Actions artifact itself is:

mule-application-1.0.1

Promotion Process
Step 1 — Developer creates a feature branch

Example:

feature/add-new-api


Make the required changes and push the branch.

Step 2 — Create Pull Request

Create a Pull Request:

feature/add-new-api
          ↓
       develop


Review and approve the Pull Request.

Step 3 — Merge to develop

After the Pull Request is merged:

develop
   ↓
ci.yml


starts automatically.

Step 4 — CI Build

ci.yml performs:

Checkout
   ↓
Setup Java
   ↓
Calculate version
   ↓
Maven Build
   ↓
Tests
   ↓
Package
   ↓
Upload Artifact


For example:

Version: 1.0.1


Artifact:

mulesoft-demo-api-1.0.1-develop-b64f946.jar

Step 5 — Automatic DEV Deployment

After the build succeeds:

Build
   ↓
Deploy DEV


The deploy-dev job calls:

reusable-deploy.yml


The workflow downloads the artifact from the same CI run.

The application is then deployed to:

CloudHub DEV


No manual action is required.

Step 6 — Verify DEV

After deployment, verify the application in CloudHub.

Check:

Application status
Application logs
Application URL
API functionality


Only promote after DEV validation is complete.

Step 7 — Promote to QA

Go to:

GitHub
    ↓
Actions
    ↓
Promote Mule Application
    ↓
Run workflow


Select:

qa


Run the workflow.

The workflow downloads the artifact from the successful CI run.

It does not rebuild the application.

Therefore:

DEV
  │
  │ same artifact
  ▼
QA


For example:

1.0.1 → DEV
1.0.1 → QA

Step 8 — Promote to UAT

After QA validation:

GitHub
    ↓
Actions
    ↓
Promote Mule Application
    ↓
Run workflow


Select:

uat


The same artifact is deployed:

1.0.1 → UAT


No new build occurs.

Step 9 — Promote to PROD

After UAT validation, the PROD GitHub Environment should have an approval gate configured.

Go to:

Settings
    ↓
Environments
    ↓
PROD
    ↓
Required reviewers


Add the required production approvers.

When the promotion workflow is run for:

prod


GitHub pauses the deployment until the required reviewer approves it.

After approval:

1.0.1 → PROD

Same Artifact Across All Environments

The most important principle of this pipeline is:

Build once
Deploy many times


Example:

                    Build
                      │
                      ▼
             1.0.1 artifact
                      │
          ┌───────────┼───────────┐
          │           │           │
          ▼           ▼           ▼
         DEV          QA          UAT
          │           │           │
          └───────────┴───────────┘
                      │
                      ▼
                     PROD


The application is not rebuilt for QA, UAT, or PROD.

This prevents differences between environments caused by rebuilding the application.

Exchange

Exchange publication is not part of this pipeline.

The CI workflow uses:

mvn clean package


instead of:

mvn clean deploy


Therefore the pipeline does not publish the application artifact to Anypoint Exchange.

The CloudHub deployment uses the already-built GitHub Actions artifact.

Maven Settings

The repository does not require Exchange credentials for this CI/CD pipeline.

Therefore:

.maven/settings.xml


is not required for Exchange publication.

If the Mule application requires authenticated Maven repositories to resolve dependencies, configure the required Maven credentials separately and never commit passwords or client secrets to Git.
